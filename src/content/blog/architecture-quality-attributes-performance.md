성능 평가에서 "평균 응답 속도"는 데이터 양이나 환경에 따라 달라질 수 있다. 이런 부분을 어떻게 해결할까?

## 핵심 원칙 6가지

### 1. 조건 고정(명세화)

- **데이터 크기**: "상품 500만 건, 인덱스 A/B/C"
- **부하 프로필**: "동시 사용자 2,000명, RPS 800, Read:Write = 9:1"
- **시나리오**: "검색 키워드, 정렬, 필터 3종 조합"
- **환경 스펙**: "vCPU 8, RAM 32GB, 지역 1개, 네트워크 10Gbps"

→ 조건을 못박고 그 **조건에서의 SLO**를 약속한다.

### 2. 평균 대신 퍼센타일

**p95/p99 지연 시간**을 목표로 삼는다. 평균은 소수의 느린 요청을 가려 버린다.

예) "검색 API p95 ≤ 800ms, p99 ≤ 1200ms"

### 3. 성능 엔벨로프(Envelopes) · 티어 목표

한 줄 목표가 아니라 **규모별 목표 테이블**로 약속한다.

예) "RPS 500 → p95 600ms / RPS 1000 → p95 900ms"

### 4. 정규화 지표

**요청/코어당 처리량**, **GB당 처리시간**, **레코드 100만 건 증가당 지연 증가폭**처럼 **스케일에 따른 기울기**를 함께 정의한다.

### 5. 용량 · 확장 규칙 명시

- "p95가 900ms 초과 5분 지속 시 **수평 확장 +1**"
- "캐시 히트율 85% 미만 시 **키-스페이스 재설계**"

**자동/수동 확장 룰**을 SLO와 연결한다.

### 6. 재현성 있는 테스트 절차

**워밍업**(JIT/캐시/GC 안정화), **고정 시드 데이터**, **테스트 시간 15~30분**, **백그라운드 잡 일시 중지**, **3회 이상 반복 + 신뢰구간**까지 절차로 못박는다.

## 예시: 온라인 쇼핑몰 "검색 API" SLO & 평가 명세

### 설계 — 성능 SLO

- **시나리오**: "검색 키워드 + 카테고리 필터 + 가격 정렬"
- **데이터 조건**: 상품 500만, 카테고리 2천, 인덱스(`name`, `price`, `category_id`)를 사용한다.
- **트래픽 조건**: 동시 사용자 2,000, RPS 목표 800, RW=9:1을 목표로 한다.
- **환경**: Web(8vCPU/32GB)×6, Search(8vCPU/32GB)×3, DB(16vCPU/64GB, 읽기 레플리카×2)를 구성한다.
- **SLO(퍼센타일)** — p95 ≤ **800ms**, p99 ≤ **1200ms**, 오류율 ≤ **0.5%**
    - 스로틀링 시 **정중한 degrade**(추천/랭킹 비활성, 기본 정렬로 폴백)를 수행한다.
- **확장 규칙** — p95 > 900ms 5분 지속 → Search 노드 **+1** (최대 6)으로 확장한다.
    - 캐시 히트율 < 85% 10분 지속 → **pre-warm & 키 전략 조정**을 수행한다.

### 평가 결과

| 항목 | 방법 | 조건 | 결과 | 판정 | 메모 |
|---|---|---|---|---|---|
| p95 지연 | 부하 테스트(JMeter) | RPS 800, 30분, 워밍업 10분 | **742ms** | Pass | 여유 58ms |
| p99 지연 | 부하 테스트 | 동조건 | **1115ms** | Pass | 한계 근접 |
| 오류율 | 부하 테스트 | 동조건 | **0.22%** | Pass | 타임아웃 일부 |
| 확장 효율 | 단계별 RPS 500/800/1000 | 같은 데이터·환경 | p95: 590/742/930ms | Pass | 선형에 근접 |
| 코어당 처리량 | 정규화 | RPS/총 vCPU | **~14 RPS/vCPU** | Pass | 기준 ≥12 |
| 캐시 히트율 | APM | Redis layer | **88%** | Pass | 목표 85%+ |
| 쿼리 계획 | DB 분석 | 실제 플랜/인덱스 | 전 범위 인덱스 사용 | Pass | 힌트 불필요 |
| GC/Stop-the-world | 프로파일 | 30분 런 | max **38ms** | Pass | ZenGC 세팅 유효 |

**개선 항목(가정)**
- RPS 1200에서 p99 1450ms로 초과 → **검색 결과 페이지네이션 window 제한**, **결과 셋 상한 200**으로 조정하고, **필터 조합 캐싱**을 추가한다.

## 규모별 목표(성능 엔벨로프) 예시

| RPS | 동시 사용자 | p95 | p99 | 오류율 | 확장 액션 |
|---|---|---|---|---|---|
| 500 | ~1200 | ≤ 600ms | ≤ 900ms | ≤ 0.3% | 없음 |
| 800 | ~2000 | ≤ 800ms | ≤ 1200ms | ≤ 0.5% | 없음 |
| 1000 | ~2600 | ≤ 950ms | ≤ 1300ms | ≤ 0.7% | Search +1 |
| 1200 | ~3200 | ≤ 1100ms | ≤ 1500ms | ≤ 1.0% | Search +2 / 캐시 튜닝 |

## 데이터 크기 변화에 대한 "기울기" 목표

- **지연 증가율**: 상품 **+100만 건**당 p95 **+60ms 이하**로 설정한다.
- **인덱스 리빌드 시간**: 500만 → 600만 증가 시 **≤ 20분**, 서비스 영향 0으로 목표한다.
- **스토리지 사용량**: 100만 건당 **+8GB 이하**(인덱스 포함)로 제한한다.

> 이렇게 "기울기(Δ)"를 잡아두면 **데이터가 커져도 목표 재설정 없이 판정**이 가능하다.

---

## 체크리스트(재현성 보장)

- 동일 데이터 스냅샷/고정 시드
- 워밍업 10분, 런 30분, 3회 반복 평균+신뢰구간
- 배경 잡(ETL/크론) 중지
- 시간 동기화, 스로틀/리트라이 정책 고정
- 결과는 **대시보드 스크린샷 + 원시 로그**로 증빙

---

## 번외: 보안 품질도 같은 방식으로

- **조건**: TLS1.3, HSTS, OWASP Top 10, 관리자 망 분리를 적용한다.
- **지표**: 크리티컬 취약점 0, High 0, Medium ≤ 2(30일 내 조치), **MTTD/MTTR** 목표를 설정한다.
- **평가**: SAST/DAST/버그바운티/침투테스트 리포트로 증빙한다.

---

### 한 줄 정리

> **성능 목표는 "조건+퍼센타일+엔벨로프+기울기+확장 규칙+재현 절차"로 명세하면 데이터·환경 변동에도 공정하고 일관되게 판단할 수 있다.**
