[앞선 글](/blog/figcraft-rendering-accuracy/)에서는 FigCraft를 이미지 검토 도구에 연결하면서 발견한 색상 차이와 효과 잘림, 내보내기 범위를 다뤘다. 이번에는 큰 이미지 보드의 로딩과 조작 중에 발견한 문제를 고친 과정을 정리했다.

이미지가 늦게 뜨는 현상에도 원인은 여럿이었다. 원본을 받는 시간, 압축을 푸는 비용, 화면을 그리는 시간과 메모리 사용량을 나누어 확인했다. 사용 중 연결이 끊기거나 특정 JPEG 입력에서 앱이 종료되는 문제도 함께 고쳤다.

범용으로 분리할 수 있는 수정은 업스트림에 PR을 보냈다. 이미지 참조 저장과 다단계 미리보기, 메모리 예산, 타일 캐시, 별도 렌더 스레드는 개발 버전에서 작업한 내용이다. 업스트림에 반영한 수정에는 해당 PR을 연결했다. 코딩 에이전트와 함께 코드를 수정하고 검증했으며 업무 자료 대신 합성 문서로 확인한 결과를 넣었다. 수치는 각 실험 당시의 조건에 따른 결과이며 모든 변경을 합친 최신 버전을 다시 측정한 값은 아니다.

## 이미지 원본과 표시용 데이터

이미지 로딩에서는 먼저 압축 파일과 디코드된 픽셀을 구분했다. 4,000×3,000 이미지 한 장을 RGBA 4바이트로 풀면 약 48MB다. JPEG 파일은 작더라도 화면에 그리는 과정에서는 더 많은 메모리가 필요할 수 있다.

보드를 축소해 놓으면 원본이 수천 픽셀인 이미지도 화면에서는 작은 카드로 보인다. 이때마다 원본 전체를 디코드해서 줄여 그리면 필요 이상의 픽셀을 다루게 된다. 그래서 화면에 표시되는 크기에 맞춰 이미지 레벨을 선택하도록 바꿨다. 레벨이 한 단계 내려갈 때 가로·세로를 각각 절반으로 줄이는 방식이다.

현재 줌 값 외에 이미지에 적용된 변환도 확인했다. 이미지가 한 축으로 눌려 있거나 회전·변환된 상태에서도 부족한 해상도를 선택하지 않도록 이미지 픽셀에서 화면 픽셀로 가는 변환을 기준으로 판단했다. 원본 크기 이상으로 보이거나 변환을 안전하게 계산할 수 없으면 원본 레벨을 사용했다.

일부 JPEG는 디코더의 scaled IDCT를 이용해 처음부터 1/2·1/4·1/8 크기로 디코드했다. 전체 이미지를 풀었다가 줄이는 비용을 피하려는 것이다. 적용할 수 없는 형식은 기존 전체 디코드 경로로 남겼고 동시에 실행하는 전체 크기 디코드 수를 제한했다. progressive JPEG는 작은 출력이라도 원본 크기의 계수를 유지할 수 있어 별도로 취급했다.

같은 이미지를 여러 렌더 작업이 동시에 요구할 때 디코드가 중복되는 것도 막았다. 하나의 작업이 만들고 다른 작업은 그 결과를 받도록 했다. 데스크톱에서는 작은 레벨을 디스크에 보관해 다시 열 때 재사용했다. 캐시 내용이 손상됐거나 생성 규칙이 달라진 경우에는 버리고 다시 만들도록 했다.

이 단계는 표시용 픽셀을 줄이는 개선이다. 문서가 원본을 전부 메모리에 가지고 있는 구조까지 해결하려면 저장·수신 경로도 바꿔야 했다.

## 문서와 이미지의 분리

기존 흐름에서는 문서와 큰 이미지 바이트가 함께 이동하는 구간이 있었다. 문서 구조만 확인하려고 접속해도 원본 전송을 기다려야 했다. 게시나 스냅샷 처리 중에는 같은 이미지 바이트를 복사하는 부담도 생겼다.

이미지를 digest로 식별하는 별도 blob으로 저장하고 문서는 참조를 갖도록 바꿨다. 게시할 때 이미지를 먼저 보내고 문서는 참조로 전송했다. 클라이언트도 원본을 다 받기 전에 문서 구조를 열고 미리보기를 표시할 수 있게 했다. 디스크 이미지 저장과 복구 경로도 함께 정리했다.

큰 파일 게시에서는 한 번에 준비하는 이미지 묶음의 기준을 512MiB에서 64MiB로 낮추고 최대 64장 단위로 처리했다. 전송 메시지를 만들면서 이미지 전체를 `to_vec()`로 다시 복사하던 부분은 이미 준비한 버퍼의 소유권을 넘기도록 바꿨다. 여기서 64MiB는 다음 이미지를 읽을지 판단하는 기준이다. 마지막 한 장 때문에 넘을 수 있으므로 프로세스 메모리 상한이라고 부르지는 않았다.

서버에서는 미리보기 생성과 업로드가 같은 자원을 사용했다. 시작 시 복구 작업과 새 업로드가 하나의 중복 제거 대기열을 사용하게 하고 사용자가 요청한 미리보기를 먼저 처리하도록 했다. 아직 만드는 중인 이미지와 실제로 없는 이미지를 구분해 재시도가 끝없이 이어지지 않도록 했다.

전송 경로에서는 협업 메시지와 이미지 바이트를 분리했다. 문서 수정과 접속 상태는 기존 세션으로 주고받고 이미지는 HTTP로 받을 수 있도록 했다. HTTP 요청이 실패했을 때 기존 세션 경로로 돌아가는 동작도 확인했다. 이 변경은 이미지 전송 때문에 협업 서버가 큰 버퍼를 계속 보관하는 부담을 줄이려는 목적이었다. 네트워크 대역폭이 병목인 경우에는 경로를 바꿔도 전체 다운로드 시간이 크게 줄지 않았다.

## 단계별 미리보기와 요청 순서

원본보다 작은 미리보기를 도입해도 보드를 아주 작게 보면 미리보기 자체가 여전히 컸다. 긴 변 1024px 이미지를 수십·수백 장 먼저 받아놓고 화면에서는 훨씬 작게 그리는 상황이 있었다.

그래서 256px 작은 미리보기, 1024px 미리보기, 원본의 세 단계로 나눴다. 작은 단계로 전체 모습을 먼저 보여주고 더 크게 볼 때 필요한 단계를 요청하도록 했다. 예전 서버에 작은 단계가 없으면 기존 미리보기로 돌아가도록 호환 경로도 두었다.

작은 미리보기의 차이는 공개 사진으로 확인했다. 아래는 같은 인물 사진에서 얼굴과 머리카락 주변을 같은 배율로 확대한 결과다. 왼쪽은 윤곽이 뭉개지고 가운데와 오른쪽에서는 머리카락과 얼굴의 세부가 더 구분된다. 보드 전체를 작게 볼 때는 작은 미리보기로 배치를 보여주고 한 장을 확대하면 더 큰 단계로 바꾸는 용도다.

요청 순서도 바꿨다. 해시맵 순서대로 받으면 지금 보고 있는 화면 바로 옆 이미지가 문서 반대편 이미지보다 늦게 올 수 있었다. 현재 그린 이미지, 화면 주변 이미지, 나머지 순서로 대기열을 재정렬했다. 브라우저의 필요 시 수신 경로에서는 화면과 주변에서 벗어난 원본을 아직 보내지 않은 대기열에서 뺐다. 이미 전송한 요청까지 취소하는 기능은 프로토콜에 없어 그 응답은 계속 받는다.

확대했다가 다시 축소할 때는 별도 문제가 나왔다. 이미 원본을 받은 이미지를 작은 크기로 다시 디코드하느라 거친 미리보기조차 늦어졌고 큰 미리보기가 작은 미리보기의 캐시 공간을 밀어냈다. 캔버스에서 충분한 해상도의 미리보기를 우선 쓰도록 하고 작은 미리보기 캐시를 분리했다. 데스크톱에서는 필요한 레벨을 병렬로 준비하도록 했다.

이미 원본이 있다는 이유만으로 원본에서 다시 계산하는 게 항상 유리하지는 않았다. 전체를 빨리 보여줘야 하는 축소 동작에서는 작게 준비된 이미지가 더 적합했다.

## 브라우저 확대·축소의 멈춤

웹에서는 이미지를 다 받은 뒤에도 확대·축소 중 화면이 멈췄다. 당시 업스트림의 브라우저 렌더러는 UI 스레드에서 작업했다. 휠 입력마다 거친 미리보기를 그린 뒤 다음 프레임에 정밀 렌더를 실행했는데 무거운 페이지에서는 그 한 번이 몇 초 걸렸다.

계속 확대하는 동안 곧 버릴 정밀 화면을 반복해서 그리는 셈이었다. 그래서 새 입력이 잠시 멈춘 뒤 정밀 렌더를 시작하도록 바꿨다. 기준은 120ms이고 마지막 정밀 렌더가 더 빨랐다면 그 시간까지만 기다리도록 했다. 가벼운 문서에서도 무조건 120ms를 기다리게 만들고 싶지는 않았다.

처음 구현에서는 대기 시작점을 요청 시각으로 잡았다. 하지만 미리보기 자체가 250ms 걸리는 페이지에서는 미리보기가 끝나기도 전에 120ms가 지나버렸다. 다음 프레임에 바로 정밀 렌더가 실행돼 기존과 비슷한 결과가 나왔다. 대기는 미리보기를 화면에 넘긴 시점부터 계산하도록 고쳤다. [PR #1468](https://github.com/storytold/figcraft/pull/1468)

![브라우저 확대·축소 실험에 사용한 합성 보드](/blog/figcraft-work-notes/synthetic-board.png)

*1500px JPEG 20장, 그림자를 넣은 사각형 60개, 배경 블러 패널 2개로 만든 82개 레이어의 합성 보드. 위 이미지는 측정에 사용한 문서의 최종 화면이며 업무 자료가 아니다.*

Chrome 156과 Apple Silicon Mac에서 같은 release 빌드 조건으로 비교했다. 50ms 간격의 확대 20회와 축소 20회 후 정밀 화면을 기다리는 동작을 각 3회 실행했다.

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 프레임 간격 중앙값 | 8.4~8.7ms | 8.3~8.5ms |
| 프레임 간격 p95 | 3.66~3.71초 | 240~249ms |
| 100ms 초과 프레임 | 79~80개 | 39~41개 |
| 40번 입력 중 미리보기가 보인 횟수 | 5~13회 | 39~40회 |
| 휠 시작부터 마지막 정밀 화면까지 | 141초 | 10~12초 |

중앙값만 보면 거의 차이가 없지만 긴 멈춤과 실제로 표시한 미리보기 수에는 차이가 있었다. 다만 미리보기 자체에 걸리는 약 250ms와 입력이 멈춘 뒤의 정밀 렌더 비용은 남았다. 이 수치는 해당 합성 보드와 입력 시나리오의 결과다.

## 정밀 렌더의 분할과 비용

다음에는 입력이 멈춘 뒤 실행하는 정밀 렌더를 가로 띠 단위로 나눴다. 한 번에 화면 전체를 완성하느라 UI를 오래 붙잡지 않도록 띠 사이에 입력을 처리할 기회를 주는 방식이다. [PR #1496](https://github.com/storytold/figcraft/pull/1496)

구현에는 24ms 작업 기준이 있지만 한 띠가 그보다 오래 걸리면 중간에 끊을 수 없다. 화면을 최대 8개 띠로 나누는 조건도 있어 무거운 문서에서 24ms 프레임을 보장하는 구조는 아니다. 작업 중 줌·문서·페이지가 바뀌면 오래된 결과를 버리고 같은 배율의 이동·편집은 완성한 결과를 갱신해 이어갈 수 있도록 상태도 나눴다.

![정밀 렌더 분할 전후의 최대 프레임과 완성 시간](/blog/figcraft-work-notes/banding-tradeoff.png)

*배경 블러가 있는 합성 보드의 실제 3회 측정값. 왼쪽은 깊게 확대한 뒤 가장 오래 걸린 프레임, 오른쪽은 입력이 멈춘 뒤 정밀 화면까지 기다린 시간이다. 새 벤치마크가 아니라 당시 원시 기록을 그래프로 옮겼다.*

| 배경 블러가 있는 페이지 | 한 번에 렌더 | 띠로 나누어 렌더 |
| --- | ---: | ---: |
| 가장 긴 프레임 | 3.7~4.0초 | 0.9~1.4초 |
| 100ms 초과 프레임 | 1개 | 8개 |
| 입력 정지 후 정밀 화면까지 | 3.8~4.1초 | 6.7~8.1초 |

한 번에 멈추는 시간은 줄었지만 화면이 완성되는 총시간은 늘었다. 배경 블러가 띠 바깥을 읽기 때문에 겹치는 영역을 다시 그려야 했고 그림자 같은 계산도 여러 띠에서 반복됐다. 블러가 없는 경우에도 분할 비용은 있었다.

이 결과는 응답성과 작업 완료 시간을 따로 봐야 한다는 근거가 됐다. 긴 작업을 나눴다고 계산량 자체가 줄어드는 것은 아니었다.

## 별도 렌더 스레드

별도 개발 버전에서는 브라우저 렌더를 Worker에서 실행하는 별도 스레드로 옮기는 작업도 했다. 메인 스레드는 마지막 화면을 표시하면서 입력을 받고 렌더 스레드는 다음 화면을 준비하도록 했다. 앞의 띠 분할 PR과는 별도 변경이며 이 기능까지 업스트림에 병합된 것은 아니다.

WASM 스레드를 켜는 빌드 설정만으로 끝나지는 않았다. 공유 메모리를 사용하려면 페이지 격리가 필요했고 메인 스레드에서 공유 메모리 대기를 하는 잠금 경로도 조정해야 했다. 렌더 캐시와 폰트 데이터, 이미지 저장소처럼 두 스레드가 함께 사용하는 부분을 확인했다.

UI 컨텍스트를 작업 스레드로 넘기는 대신 깨워야 한다는 신호를 남겨 메인 스레드가 처리하게 했다. 공유 메모리의 뷰를 그대로 넘길 수 없는 WebSocket·난수 API 경계에서는 바이트를 복사했다. Worker가 시작하지 못하거나 종료되면 최신 작업을 기존 inline 렌더러로 다시 보내는 fallback도 만들었다.

이후에는 SIMD 빌드도 비교했지만 당시 확인한 메인 스레드 프레임 지표에서 이득이 뚜렷하지 않았다. 렌더가 이미 다른 스레드에 있어 그 지표만으로 연산 최적화의 효과를 판단하기 어려웠고 바이너리 크기는 늘었다. 이 실험의 SIMD 빌드는 도입하지 않았다.

## 화면 재사용과 부분 갱신

한 번 본 위치나 배율로 돌아갈 때마다 전체 화면을 다시 그리는 비용도 줄였다. 이전 렌더 결과를 512px 격자의 타일로 보관하고 같은 배율에서 재사용하도록 했다. 타일 캐시에는 128MiB 예산을 두고 오래 쓰지 않은 항목부터 내렸다. 문서가 바뀌거나 효과·이미지 조건이 달라지면 해당 결과를 재사용하지 않도록 했다.

이미지 한 장이 도착할 때 전체 화면을 무효화하는 동작도 바꿨다. 도착한 이미지의 digest를 렌더러까지 전달하고 그 이미지를 쓰는 노드와 영향을 받는 영역만 다시 계산했다. 여러 노드가 같은 이미지를 쓰거나 마스크·부모 효과·배경 블러가 얽힌 경우도 포함해야 했다. 변경 이력을 놓쳤거나 영향 범위를 안전하게 계산할 수 없는 경우에는 전체 렌더로 돌아갔다.

## 캐시와 메모리 예산

모두 캐시라고 부르지만 저장하는 데이터와 줄이려는 비용은 달랐다. HTTP 캐시는 다시 받는 바이트를 줄이고 IndexedDB의 명시적 보관은 사용자가 선택한 문서의 이미지를 기기에 남긴다. 디코드 캐시는 압축을 다시 푸는 비용을 줄이고 화면 타일은 이미 그린 결과를 재사용한다.

메모리에서 미리보기를 내렸다고 서버에 그 이미지가 없다는 뜻은 아니다. 이 상태를 구분하지 않으면 다시 화면으로 돌아왔을 때 재요청하지 못한다. 반대로 예산이 부족할 때마다 같은 이미지를 받고 버리는 일을 반복할 수도 있다. 실제 읽기에 따라 LRU 순서를 갱신하고 현재 화면의 수요와 일시적인 메모리 압박을 별도 상태로 관리했다.

수신과 디코드에는 공통 예약 예산을 붙였다. 기본 관리 예산은 1GiB이고 보관 중인 버퍼가 최대 768MiB를 쓰게 해 256MiB를 작업 공간으로 남겼다. 요청하기 전에 공간을 예약하고 수신·검사·디코드가 버퍼를 넘겨받을 때 예약도 함께 이동하도록 했다.

Rust의 `Arc` 수명도 중요했다. 캐시에서 항목을 삭제해도 렌더 작업이 참조하고 있으면 실제 메모리는 살아 있다. 이때 예산부터 반환하면 장부에는 공간이 있는 것처럼 보인다. 마지막 소유자가 참조를 해제할 때까지 예산 계산에 포함하고 타임아웃이 나도 실제 비동기 읽기가 끝나지 않았다면 예약을 유지했다.

문서 원본과 undo 기록까지 이 예산으로 제한한 것은 아니다. GPU 텍스처나 브라우저 내부 버퍼, 할당기 여유 공간도 따로 존재한다. 관리 예산 1GiB는 프로세스 RSS의 상한이 아니다.

실제 브라우저 검증에서는 작은 이미지마다 최대 blob 크기인 128MiB를 예약해 IndexedDB 동시 읽기가 막히는 문제를 찾았다. 저장된 데이터가 있는데 HTTP로 다시 받는 일이 생겼다. 인덱스에 기록된 길이의 2배를 먼저 예약하고 실제 길이와 digest를 확인하도록 수정했다.

합성 이미지 96개, 압축 원본 합계 4,284,757바이트를 기기에 보관해 확인했다. 저장된 길이와 SHA-256은 모두 같았다. HTTP 캐시를 끄고 다시 열어도 원본 HTTP 요청은 0건이었고 기기 보관을 해제한 다음에는 96개를 다시 받았다. 일반 문서에서는 이후 HTTP 캐시로 96개를 재사용했다. 이 시험의 이미지는 별도 서버 미리보기를 만들지 않는 크기라 미리보기 LRU 압박까지 검증한 것으로 보지는 않았다.

## 오래 실행했을 때의 동작

짧은 기능 시험 뒤에는 같은 합성 이미지 96개를 여러 배율로 반복해서 렌더링했다. 20분 동안 26,654회 실행했고 오류와 관리 예산 초과는 없었다. 렌더 뒤 관리 대상 바이트는 510MiB로 유지됐다. 이 시험의 RSS 최고값은 540.6MiB, 종료 시점은 274.5MiB였다.

이 시험은 사람이 20분 동안 화면을 조작한 결과와는 구분해야 한다. macOS가 창을 숨김으로 판단한 구간에서 UI 렌더가 멈춰 `ui.render`를 직접 호출하는 방식으로 보완한 실행이다. 실제 입력 지연과 장시간 UI 조작은 별도로 측정해야 한다.

협업은 실제 데스크톱 앱 두 개와 합성 문서로 확인했다. 서로 다른 객체 수정, 같은 속성의 경합, 동시 생성, 삭제와 수정의 경합, 실행 취소, 정상 서버 재시작 후 재접속을 두 번 실행했다. 상태 일치 검사는 총 67회 통과했고 새로 접속한 세 번째 앱의 최종 문서와 PNG 출력도 일치했다.

다만 같은 속성은 서버 처리 순서의 마지막 쓰기가 남았다. X와 Y도 하나의 변환 속성이라 서로 다른 축을 수정했다고 두 의도가 모두 합쳐지지는 않았다. 텍스트 전체 교체도 한쪽 문자열이 남았다. 모든 클라이언트가 같은 상태가 되는 것과 모든 편집 의도를 보존하는 것은 달랐다.

별도 부하 시험에서는 합성 문서로 최대 22연결을 확인한 뒤 가상 열람 10개·편집 5개와 실제 Chrome 2개를 20분 유지했다. 지속 구간의 11,740개 편집 배치가 모든 가상 클라이언트에서 같은 최종 속성으로 수렴했고 다른 클라이언트 수신 지연 p95는 115ms였다. 가상 클라이언트는 실제 프로토콜과 이미지 수신은 수행하지만 브라우저 디코딩을 하지 않는다. 따라서 실제 브라우저 22개의 최대 수용량 시험으로 해석할 수는 없다.

## 접속 유지 ping의 기준

업스트림에 처음 보낸 수정은 크기가 작고 독립적인 접속 유지 버그였다. 혼자 접속한 사용자가 포인터를 계속 움직이면 약 45초마다 연결이 끊기는 현상이 있었다.

클라이언트는 포인터 움직임을 presence 메시지로 보냈다. 그런데 모든 송신이 다음 ping을 15초 뒤로 미뤘다. 계속 움직이면 ping이 나가지 않았고 혼자 있는 세션에서 서버는 presence에 응답할 이유가 없어 클라이언트가 아무것도 받지 못했다. 45초 수신 유휴 제한이 지나면 정상 연결을 스스로 끊었다.

ping을 마지막 메시지 송신이 아닌 마지막 ping 시각 기준으로 보내도록 바꿨다. presence를 계속 보내도 15초마다 ping이 나가도록 했다. 90초 동안 초당 10회 presence를 보내고 서버는 ping에만 응답하는 테스트를 추가했다. 기존 코드에서는 끊기고 수정 후에는 연결이 유지됐다. [PR #1424](https://github.com/storytold/figcraft/pull/1424)

메시지를 계속 보내더라도 서버의 응답을 받고 있는지는 별도로 확인해야 했다.

## JPEG 크래시와 제어 입력

이미지를 다루면서 디코더의 panic도 확인했다. 당시 `zune-jpeg 0.5.15`는 첫 번째 성분보다 뒤쪽 성분의 샘플링이 더 촘촘한 progressive JPEG에서 문제가 있었다. 큰 이미지가 아니어도 8×8 파일로 재현됐다.

CLI에서는 썸네일을 쓰다가 종료됐고 데스크톱에서는 그리기마다 guard가 panic을 받았으며 브라우저에서는 탭 실행이 중단됐다. 공통 디코드 진입점에서 JPEG frame header를 확인하고 해당 조건을 디코더에 넘기기 전에 거절하도록 했다. 정상 progressive JPEG와 baseline CMYK는 계속 처리하는 테스트를 함께 넣었다. [PR #1491](https://github.com/storytold/figcraft/pull/1491)

이 수정은 문제가 있는 JPEG를 복원하지 못한다. 지원하지 못하는 입력 하나 때문에 앱 전체가 종료되는 것을 막는다. 해당 이미지 자리에는 빈 영역이 남고 일반 이미지의 출력은 유지된다. 라이브러리 수정이 안정 버전으로 들어오면 제거할 수 있도록 임시 검사라는 점도 코드에 남겼다.

성능 측정을 자동화하다가 웹 제어 채널의 `ui.input`이 끝나지 않는 문제도 찾았다. 브라우저에서는 명령 실행과 스크린샷은 되는데 포인터·키보드 입력은 큐에 남아 있었다. 데스크톱에 있던 `raw_input_hook`이 웹 셸에 없어 입력 배치를 현재 프레임으로 넘기지 못한 것이었다.

웹 셸에도 훅을 연결하고 실제 Chrome에서 도구 전환 키와 사각형 드래그를 확인했다. 변경 전에는 5초 타임아웃이 났고 변경 후에는 입력이 적용되고 응답도 돌아왔다. 수정 코드가 짧아도 브라우저 실행 경로를 통과하는지는 따로 확인해야 했다. [PR #1499](https://github.com/storytold/figcraft/pull/1499)

## 후속 작업과 보류한 개선

웹 제어 입력을 연결한 #1499 뒤에는 문서 전환과 입력 묶음의 경합이 남았다. 문서 A에 입력을 보낸 직후 B로 전환하면 입력이 B에 적용되는데도 성공 응답이 돌아올 수 있다. [이슈 #1503](https://github.com/storytold/figcraft/issues/1503)의 후속 작업에서는 실제 입력 처리 직전에 문서를 다시 확인하고 대상이 바뀌었다면 실패 응답과 함께 해당 입력 자체도 막아야 한다. 2026년 10월 30일 다시 확인했으며 이슈는 열려 있다. 아직 완료한 수정은 아니다.

이전 프레임을 늘여 보여주는 방식과 타일 캐시의 업스트림 반영은 보류했다. [GPU 렌더러 PR #1456](https://github.com/storytold/figcraft/pull/1456)에서 관리자는 웹을 포함한 CPU 렌더러가 상태를 갖지 않아야 한다는 방향을 밝혔다. 별도 개발 버전에서 동작하더라도 업스트림의 구조와 맞는지는 다시 판단해야 했다. 캐시 개선의 업스트림 도입 여부는 아직 정하지 않았다.

## 남은 작업과 소감

내보내기는 원본이 준비되지 않았거나 메모리가 부족할 때 이미지가 빠진 결과를 성공으로 반환하지 않도록 했다. 하지만 원본 준비가 끝나면 자동으로 재개하거나 메모리보다 큰 원본 전체를 순차적으로 읽어 출력하는 흐름은 아직 후속 작업이다. GPU 부분 업로드, 로컬 원본을 필요한 시점까지 읽지 않는 방식, 텍스트·공간 검색 비용도 별도로 남아 있다.

이번 작업에서는 느리다는 현상을 여러 단계로 나누어 보게 됐다. 다운로드가 줄어도 디코드는 남고 CPU 재렌더 면적이 줄어도 GPU 업로드량은 같을 수 있었다. 프레임 중앙값이 비슷해도 몇 초씩 멈추는 구간은 크게 달랐다. 각 단계에서 무엇을 줄였는지 확인해야 다음에 어디를 볼지 정할 수 있었다.

처음 필요했던 건 이미지 검토 작업을 돕는 기능이었다. 실제로 연결하고 검증하면서 파일·네트워크·화면 표시의 경계에서 문제를 하나씩 찾았다. 고친 내용 중 다른 사용자에게도 도움이 될 만한 것을 정리해 보내다 보니 오픈소스 기여까지 이어졌다. 다른 환경에서도 재현할 수 있도록 문제를 좁히고 수정 이유를 설명하는 과정에서도 배운 것이 많았다.
