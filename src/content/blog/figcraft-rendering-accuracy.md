여러 이미지를 보드에 모아 검토하는 작업을 돕는 도구를 개발하고 있었다. 내가 이미지를 검토하는 것은 아니고 실제로 그 일을 하는 사람들이 파일을 열고 정리하는 데 드는 수고를 줄이는 쪽이었다. 보드를 자동으로 구성하고 기존 작업을 이어갈 수 있는지 살펴보다가 FigCraft를 사용하게 됐다.

[FigCraft](https://github.com/storytold/figcraft)는 Rust로 만든 인터페이스 디자인·프로토타이핑 도구다. 데스크톱과 웹에서 사용할 수 있고 CLI와 제어 채널도 있어서 화면을 직접 조작하는 것 외에 코드로 문서를 만들고 동작을 확인할 수 있었다. 처음에는 이 부분이 필요했다.

실제로 연결해보니 보드 구성 외에도 손볼 곳이 있었다. 사진이 다른 뷰어와 다르게 보였고 큰 파일을 열면 이미지가 표시되기까지 오래 걸렸다. 브라우저에서 확대·축소할 때 화면이 멈추기도 했다. 도구를 붙이는 작업이 이미지 저장과 전송, 렌더링, 메모리 관리까지 이어졌다.

이 기록은 두 편으로 나눴다. 첫 편에서는 사진의 색과 레이어 효과, 내보낸 이미지의 범위를 수정한 과정을 다룬다. 이미지 로딩과 메모리, 렌더링 성능과 연결 안정성은 다음 편에 담았다. 업무별 구성이나 실제 자료는 제외하고 공개 재현에 사용한 합성 보드와 공개 사진으로 다시 촬영한 색 비교를 넣었다. 코딩 에이전트와 함께 코드를 수정하고 검증했다. 아래의 수치는 각 실험 당시의 조건과 함께 적었으며 모든 변경을 합친 최신 버전을 처음부터 다시 측정한 결과는 아니다.

## 보드 구성에서 사용 흐름까지

처음 연결한 기능은 로컬 프로그램에서 FigCraft로 보드와 이미지를 자동으로 올리는 것이었다. 로컬에서 만든 결과를 FigCraft 파일로 구성하고 이미지를 배치해 파일을 하나씩 옮기는 수고를 줄이려 했다.

로컬 파일과 서버에 공유한 파일을 구분하는 것도 필요했다. 같은 이름이라고 같은 상태의 문서는 아니었다. 로컬 사본을 열어놓고 서버와 동기화된다고 생각하면 작업 결과를 잘못 이해할 수 있어서 목록과 표시를 나눴다. 원격 파일 검색과 폴더 탐색, 첨부파일의 업로드·다운로드도 추가했다. 첨부파일은 화면에서 열리는지 확인하고 내려받은 바이트가 원본과 같은지도 비교했다.

큰 파일은 페이지별로 나누어 가져올 수 있게 했고 같은 문서를 다시 올릴 때 기존 공유 링크를 유지하는 갱신 흐름도 만들었다. 문서와 페이지의 식별자를 보고 기존 대상을 찾도록 했다. 파일 이름만으로 새 문서인지 수정본인지 판단하지 않으려는 선택이었다.

큰 문서를 여러 번 열어보니 이미지의 색이 원래 보던 것과 미묘하게 달랐다. 웹브라우저에서는 로딩이 오래 걸리고 확대·축소 중 화면이 멈추기도 했다. 이런 현상들을 확인하다 보니 근본적인 원인을 찾기 위해 이미지가 내부에서 어떻게 처리되고 화면에 그려지는지 더 깊이 들여다보게 됐다.

## 파일과 화면의 색 차이

기존에 Figma에서 작업하던 파일을 FigCraft로 불러와 확인하던 중 이미지가 묘하게 다르다는 느낌을 받았다. 같은 이미지인데 색이 원래 보던 것과 조금 달랐다.

처음에는 파일을 가져오는 과정에서 이미지가 바뀐 것인지 화면에 표시하는 방식이 다른 것인지 알 수 없었다. 같은 이미지를 다른 뷰어에서도 열어봤다. FigCraft에서 내려받은 파일은 다른 뷰어에서 정상적으로 보여서 저장된 이미지보다 화면에 표시되는 과정을 살펴보기 시작했다.

원본 이미지, GPU surface의 픽셀, 운영체제가 화면에 표시한 결과를 차례로 확인했다. 앱의 `ui.screenshot`으로 surface를 읽고 macOS의 `screencapture`로 화면을 캡처했다. 화면 캡처에는 Display P3 프로필이 붙어 있어 sRGB로 변환한 뒤 원본과 비교했다. RGB 숫자만 바로 비교하면 서로 다른 색 공간의 값을 같은 것으로 취급하게 된다.

FigCraft가 당시 사용하던 `wgpu-hal 30.0.1`은 sRGB surface의 Metal layer에 색 공간을 명시하지 않고 있었다. 이 경로에서 `CAMetalLayer.colorspace`가 `nil`이면 sRGB 픽셀을 디스플레이의 색 공간에 맞게 변환하는 처리가 빠졌다. 넓은 색역의 화면에서는 유채색이 더 진하게 보였고 회색·흰색은 그대로였다. [공개 재현 이슈 #1538](https://github.com/storytold/figcraft/issues/1538)

수정은 이미지에 보정을 적용하는 방식이 아니었다. surface의 색 공간을 명시했다.

```rust
// 기존
wgt::SurfaceColorSpace::Srgb => None,

// 수정
wgt::SurfaceColorSpace::Srgb => {
    Some(unsafe { objc2_core_graphics::kCGColorSpaceSRGB })
},
```

색 견본만으로는 화면에서 느낀 차이가 잘 드러나지 않아 공개 사진으로도 확인했다. 아래는 왼쪽부터 원본 사진, 패치 전 공식 FigCraft 0.12.1, 색 공간 패치를 적용한 개발 빌드다. 주황색 옷과 피부색을 보면 차이를 확인하기 쉽다.

### 화면 표시 오차

각 앱이 GPU에 그린 픽셀을 기준으로 실제 화면 캡처를 sRGB로 변환한 값과 비교했다. 아래는 RGB 각 채널의 평균 절대 오차다. 값의 범위는 0~255이며 작을수록 앱이 그린 픽셀과 화면 표시가 가깝다. 이 값은 RGB 픽셀 값이 얼마나 달라졌는지를 나타낸다. 사람이 느끼는 색 차이를 평가하는 ΔE를 계산한 것은 아니다.

| 측정 영역 | 공식 0.12.1 · 패치 전 | 패치 적용 빌드 |
| --- | ---: | ---: |
| 얼굴 | 3.794 | 0.121 |
| 주황색 옷 | 10.993 | 0.154 |
| 밝은 배경 | 1.231 | 0.149 |

주황색 옷에서 표시 오차가 가장 컸고 패치 적용 빌드에서는 세 영역 모두 작아졌다. 화면 전환으로 보이는 차이와 이 수치를 함께 확인했다. 보는 사람의 디스플레이와 브라우저 색 관리에 따라 눈에 보이는 차이는 달라질 수 있다.

이번 사진 비교는 공식 배포본과 별도 개발 빌드 사이의 비교다. 색 패치 한 줄만 다른 동일 빌드 A/B는 아니며 두 앱의 확대 샘플링에도 작은 차이가 있다. 그래서 두 앱의 화면을 서로 빼서 비교하는 대신 각 앱이 그린 픽셀과 실제 화면 표시 사이의 차이를 따로 확인했다.

앞선 2026년 10월 29일에는 Apple M3, 내장 Liquid Retina XDR, macOS 26, FigCraft 0.12.1 조건에서 8색 견본으로 측정했다. 공개 이슈와 백포트 PR에는 이 결과를 첨부했다.

| 견본 | 원본 RGB | 수정 전 화면을 sRGB로 변환 | 수정 후 |
| --- | --- | --- | --- |
| 피부색 계열 | 224, 172, 146 | 234, 169, 142 | 224, 172, 146 |
| 청록 | 0, 128, 128 | 0, 130, 129 | 0, 128, 128 |
| 회색·흰색·검정 | 기준값 | 변화 없음 | 변화 없음 |

이번 견본 전체의 최대 채널 오차는 10에서 3으로 줄었다. 앞서 다른 견본으로 얻었던 51→1 결과와는 입력과 조건이 달라 같은 실험처럼 합치지 않았다. 처음에는 색이 옅어 보인다는 관찰도 있었지만 이번 재현에서는 색이 더 진하게 보였다. 두 관찰을 모두 같은 원인으로 설명할 수 있다고 단정하지 않았다.

색 공간을 명시하는 수정 자체는 기존에 공개된 패치다. wgpu의 [기존 수정 #10286](https://github.com/gfx-rs/wgpu/pull/10286)을 확인해 로컬에서 적용했고 사용 중인 v30 계열에도 들어가도록 [백포트 PR #10780](https://github.com/gfx-rs/wgpu/pull/10780)을 올렸다. 원 작성자의 저자 정보를 유지하고 측정 결과를 첨부했다. 2026년 10월 30일 확인 시 이 PR은 열려 있다.

## 블러와 그림자의 경계

웹에서 긴 멈춤을 줄이려고 화면을 가로 띠로 나누어 그리는 작업도 했다. 이 작업을 리뷰하면서 여러 효과가 겹칠 때의 경계 계산을 더 살펴보게 됐다. 분할 렌더링의 성능과 비용은 다음 편에서 다룬다.

한 레이어에 블러와 텍스처를 순서대로 적용하면 픽셀이 퍼지는 범위가 누적된다. 그런데 기존 계산은 효과 하나의 최대 범위만 사용했다. 레이어가 화면이나 띠 경계에 걸리면 안쪽까지 영향을 주어야 할 내용이 잘렸다.

화면 렌더에서는 누적되는 효과의 범위를 더해 안전한 여백을 확보했다. 배경 블러가 겹친 경우에는 띠의 겹침 범위도 확인했다. 전체 렌더와 분할 렌더를 비교할 때는 렌더러가 스냅한 실제 뷰 크기를 기준으로 맞췄다. 원래 요청한 뷰와 비교하면 한 픽셀 차이 때문에 행이 달라져 잘못된 결함처럼 보일 수 있었다. [PR #1583](https://github.com/storytold/figcraft/pull/1583)

이 문제는 분할 렌더링 PR #1496의 병합 직전 CodeRabbit이 남긴 리뷰에서 시작했다. 처음에는 그림자의 차이가 작다고 봤지만 추가 리뷰에서 장면을 바꾸자 훨씬 큰 잘림이 드러났다. 블러가 적용된 레이어에서 그림자를 만들기 때문에 그림자의 위치까지 포함한 장면으로 확인해야 했다.

아래는 초록색 사각형에 블러를 적용하고 그림자를 아래쪽으로 멀리 떨어뜨린 재현 장면이다. 초록색은 원래 도형이고 검은색은 그 도형의 그림자다. 점선으로 표시한 아래쪽 영역만 화면에 들어오는 상황을 비교했다. 도형 자체가 화면 밖에 있더라도 이 영역에 걸치는 그림자는 그대로 보여야 한다.

이제 표시한 영역을 나란히 놓고 **각 이미지의 위쪽 중앙에 남아 있는 검은 부분**을 보면 된다. 왼쪽은 전체 장면을 렌더한 뒤 해당 영역을 뽑은 기준이다. 가운데와 오른쪽은 처음부터 이 영역만 화면에 들어오도록 렌더했다. 따라서 세 이미지에는 초록색 도형이 없고 그림자의 아래쪽만 보인다.

| 기준: 전체 렌더의 같은 영역 | 수정 전: 경계에서 렌더 | 수정 후: 경계에서 렌더 |
| --- | --- | --- |
| [![전체 렌더에서 뽑은 그림자 기준 영역](/blog/figcraft-work-notes/shadow-reference.png)](/blog/figcraft-work-notes/shadow-reference.png) | [![수정 전 경계 렌더에서 잘린 그림자](/blog/figcraft-work-notes/shadow-before.png)](/blog/figcraft-work-notes/shadow-before.png) | [![수정 후 기준과 일치하는 그림자](/blog/figcraft-work-notes/shadow-after.png)](/blog/figcraft-work-notes/shadow-after.png) |

가운데의 수정 전 이미지에서는 검은 그림자가 대부분 사라지고 희미한 회색 흔적만 남는다. 화면 밖의 도형을 계산할 때 블러가 퍼지는 범위를 충분히 남기지 않아 그 도형으로 만들 그림자도 함께 잘린 것이다. 오른쪽의 수정 후 이미지에서는 위쪽 중앙의 검은 부분과 아래로 흐려지는 모양이 기준과 같아졌다. 그림자 설정은 그대로 두고 **화면 위치가 바뀌어도 보여야 할 그림자가 유지되도록** 고쳤다.

*반경 50 블러, 아래로 300 이동한 그림자, y=390부터의 뷰를 사용했다. 2026년 10월 30일 FigCraft 렌더러로 새로 만든 합성 장면이다. 세 이미지 모두 400×210픽셀이며 같은 크기로 표시했다. 수정 전은 #1583 이전의 `effect_margin` 계산, 수정 후는 해당 수정이 적용된 계산이다. 밝기·채도 보정이나 차이 강조는 하지 않았다. 이미지를 누르면 원본을 볼 수 있다.*

![겹친 효과의 렌더 경계 수정 전후 채널 차이](/blog/figcraft-work-notes/effect-margin-results.png)

*PR #1583에 기록한 재현 결과를 그래프로 옮겼다. 주황색은 수정 전, 청록색은 수정 후다. 실제 화면 캡처가 아니라 한 덩어리 렌더와의 최대 채널 차이를 표시한 그래프다.*

| 장면 | 수정 전 최대 채널 차이 | 수정 후 |
| --- | ---: | ---: |
| 반경 25 블러 4개, 웹 64행 띠 | 8 | 0 |
| 반경 25 블러 4개, 데스크톱 병렬 띠 | 3 | 0 |
| 반경 50 블러와 아래로 300 이동한 그림자, 잘린 뷰 | 143 | 0 |

한 덩어리로 렌더한 결과와 비교한 0~255 채널 값의 최대 차이다. 그림자 장면은 띠 분할 없이도 뷰가 레이어를 자르면 발생했다. 넘침 방지 테스트가 수정 전에도 통과한다는 후속 리뷰도 반영했다. 장면 선택과 실패 조건을 함께 확인한 작업이었다. [PR #1583](https://github.com/storytold/figcraft/pull/1583)

## 내보내기 영역

내보내기에도 같은 계열의 문제가 남아 별도 PR로 나눴다. 여러 Gaussian blur의 범위는 제곱합의 제곱근으로 합치고 텍스처 범위를 더했다. 그림자는 그 결과에서 만들어지므로 원래의 날카로운 도형이 아닌 효과 적용 후 범위를 기준으로 확장했다. 모든 범위를 단순히 더하면 안전하지만 불필요한 투명 여백이 커졌다. [PR #1589](https://github.com/storytold/figcraft/pull/1589)

![내보내기 가장자리 알파와 출력 범위 계산 비교](/blog/figcraft-work-notes/export-bound-results.png)

*PR #1589의 기록. 왼쪽은 수정 전 이미지 가장자리에 남은 알파이며 수정 후에는 다섯 장면 모두 0이었다. 오른쪽은 수정 전후가 아니라 두 가지 범위 계산 방법의 비교다. 반경을 단순히 더한 340×340과 제곱합으로 계산한 190×190 모두 효과를 담지만 투명 여백의 크기가 다르다.*

| 40×40 사각형의 효과 | 수정 전 출력 크기 | 수정 후 | 가장자리 최대 알파, 전→후 |
| --- | ---: | ---: | ---: |
| 반경 25 블러 4개 | 115×115 | 190×190 | 3→0 |
| 반경 10 블러 8개 | 70×70 | 125×125 | 10→0 |
| 반경 3 블러 16개 | 49×49 | 76×76 | 17→0 |
| 반경 15 블러 2개 + 텍스처 12 | 85×85 | 128×128 | 27→0 |
| 반경 20 블러 + 아래로 30 이동한 선명한 그림자 | 100×100 | 100×130 | 126→0 |

알파는 0~255 범위이며 이 시험에서는 가장자리가 0이면 효과가 투명 영역 안에 들어온 것으로 봤다. 반경을 단순히 더하면 반경 25 블러 4개의 출력은 340×340이 된다. 제곱합 방식으로는 같은 효과를 190×190 안에 담아 불필요한 투명 여백을 줄였다. 다만 효과를 온전히 담도록 출력이 커지면서 16,384픽셀 제한에 가까운 내보내기는 크기 제한에 걸릴 수 있다. 화면 렌더 여백과 내보내기 범위를 따로 계산한 이유다.

## SVG의 블러와 그림자

PNG의 출력 범위를 고친 뒤에는 SVG에서 효과를 표현하는 순서를 확인했다. 기존 SVG 필터는 블러마다 원본인 `SourceGraphic`에서 다시 시작하고 같은 결과 이름을 사용했다. 블러를 여러 개 쌓아도 마지막 블러 하나만 남았고 그림자도 블러 적용 전의 `SourceAlpha`에서 만들었다.

각 블러가 앞선 블러의 결과를 읽도록 연결하고 마지막 블러의 알파에서 그림자를 만들도록 바꿨다. 가져오기에서도 이 구조를 읽도록 했다. 반경 12와 16의 블러는 같은 세기의 블러 하나인 반경 20으로 돌아온다. 효과 목록 자체를 그대로 복원하는 방식은 아니다.

SVG 예시는 앞의 초록색 도형과 다른 장면이다. 이번에는 파란 사각형에 블러 두 개와 아래쪽 그림자를 적용했다. 한 번 흐린 결과를 다시 흐리므로 파란 윤곽은 더 넓고 부드럽게 퍼지고 그림자도 그 흐려진 도형을 바탕으로 만들어져야 한다. SVG로 저장했다가 다시 열어도 이 모습이 유지되는지 확인했다.

아래에서는 **파란 도형의 좌우 윤곽과 그 바로 아래 검은 그림자**를 보면 된다. 왼쪽은 저장 전 캔버스다. 가운데와 오른쪽은 각각 수정 전후 코드로 SVG를 내보내고 다시 가져와 캔버스에 그린 결과다. 작은 화면에서는 차이가 미묘하므로 이미지를 눌러 같은 부분을 크게 보면 구분하기 쉽다.

| 기준: 원래 캔버스 | 수정 전: SVG 왕복 | 수정 후: SVG 왕복 |
| --- | --- | --- |
| [![SVG 내보내기 전 기준 캔버스](/blog/figcraft-work-notes/svg-reference.png)](/blog/figcraft-work-notes/svg-reference.png) | [![수정 전 SVG 왕복 후 블러와 그림자](/blog/figcraft-work-notes/svg-before.png)](/blog/figcraft-work-notes/svg-before.png) | [![수정 후 SVG 왕복 후 블러와 그림자](/blog/figcraft-work-notes/svg-after.png)](/blog/figcraft-work-notes/svg-after.png) |

가운데는 블러 두 개 중 마지막 것만 남아서 파란 윤곽이 기준보다 덜 퍼진다. 아래쪽 검은 그림자도 블러를 적용하기 전 도형에서 만들어져 더 또렷한 띠처럼 보인다. 오른쪽은 파란 윤곽과 검은 부분이 기준처럼 부드럽게 퍼진다. **저장 전에 설정한 효과를 다시 열었을 때도 유지하도록** 고친 결과다. 수정 후에도 작은 픽셀 차이는 남는다.

*80×50 사각형에 반경 12·16 블러와 아래로 24 이동한 그림자를 사용했다. 2026년 10월 30일 새로 렌더했다. 세 이미지 모두 220×220픽셀이며 각 도형의 렌더 경계를 기준으로 정렬했다. #1598 전후의 SVG 내보내기·가져오기 코드를 사용했다. 브라우저가 SVG를 직접 표시한 화면이 아니라 FigCraft로 다시 가져온 결과다. 아래 도식은 이 차이를 만든 처리 순서를 설명한다.*

![SVG 블러와 그림자의 처리 순서 수정 전후](/blog/figcraft-work-notes/svg-blur-chain.png)

*PR #1598의 처리 순서를 설명한 도식이며 실제 렌더 결과는 아니다. 수정 전에는 두 블러가 각각 원본에서 시작했고 수정 후에는 앞선 블러의 결과를 다음 블러가 받아 마지막 결과의 알파로 그림자를 만든다.*

반경 12·16 블러와 그림자가 있는 사각형을 SVG로 내보내고 다시 가져와 캔버스에 그렸을 때 원본과의 차이는 73레벨에서 5레벨로 줄었다. 0~255 채널 값 중 가장 차이가 큰 값이다. 이미지 전체의 평균 차이나 달라진 면적을 뜻하지 않으며 모든 SVG에서 픽셀이 완전히 같아졌다는 뜻도 아니다. [PR #1598](https://github.com/storytold/figcraft/pull/1598)

추가 리뷰에서는 오프셋이 0인 그림자, 즉 글로우를 다시 가져오면 효과가 사라지는 경우와 외부 SVG의 색 복사본을 검은 그림자로 잘못 읽는 경우를 찾았다. 두 경우를 수정하고 회귀 테스트에 넣었다. 도형으로 만드는 spread 그림자와 커버 이미지로 잘라낸 그림자의 재가져오기는 여전히 지원 범위 밖이다.

## 업스트림 반영

개발 버전의 모든 변경을 그대로 업스트림에 보내지는 않았다. 범용 버그와 독립적으로 설명할 수 있는 개선을 골라 업스트림의 현재 코드에 맞춰 다시 적용했다. 로컬에서 가능한 기능도 이미지 레벨이나 참조 수신 같은 선행 구조에 의존하면 작은 PR 하나로 분리하기 어려웠다.

PR에는 재현 조건, 수정한 동작, 측정 결과와 비용을 함께 적었다. 테스트가 실패했을 때는 변경 없는 main에서도 같은 실패가 나는지 확인했다. 환경에서 이미 실패하는 테스트를 숨기거나 전체 CI가 모두 통과했다고 적지 않았다. 공개 PR에는 코딩 에이전트를 사용했다는 점도 남겼다.

2026년 10월 30일 GitHub에서 확인한 상태다. 병합은 업스트림 코드에 들어갔다는 뜻이며 모든 배포 바이너리에 포함됐다는 뜻은 아니다.

## 남은 작업

색상 문제에서는 GPU가 그린 픽셀과 운영체제가 표시한 화면을 나누어 확인했고 효과 잘림에서는 화면 렌더와 내보내기의 범위를 각각 수정했다. 같은 이미지가 다르게 보이더라도 확인해야 할 단계는 달랐다.

그룹과 클립 없는 프레임의 레이어 잘림은 [PR #1603](https://github.com/storytold/figcraft/pull/1603)으로 수정했고 2026년 10월 30일 병합됐다. 자식 영역을 합쳐 부모 레이어의 크기를 정하면서 부모의 블러·그림자 범위를 더하지 않아 자식이 부모 상자 밖까지 그려지는 장면에서 효과가 잘렸다. 자식들이 그리는 영역에 부모 효과의 범위도 더하도록 바꿨다.

블러가 있는 그룹과 클립 없는 프레임의 세 재현 장면에서 기준 화면과의 최대 채널 차이는 각각 116·245·116에서 모두 0으로 줄었다. 기존 부분 렌더 테스트는 전체 렌더와 부분 렌더 양쪽에서 같은 그림자가 잘려도 통과하고 있었다. 두 결과가 같다는 것만으로는 충분하지 않아 효과가 잘리지 않는 기준 화면과도 비교했다. 다만 축소 변환이 적용된 컨테이너의 효과 잘림과 부분 갱신 범위를 필요 이상으로 넓게 잡는 문제는 이번 수정 범위에 포함하지 않았다.

macOS 색 관리 [이슈 #1538](https://github.com/storytold/figcraft/issues/1538)도 남아 있다. 로컬 패치의 표시 결과는 확인했지만 wgpu v30 백포트는 아직 리뷰 대기 중이다. VectorCraft가 채택한 앱 쪽 우회처럼 Metal 레이어에 sRGB를 직접 지정하는 방법도 검토 대상이다. 다만 이 방식에는 `unsafe`가 필요하고 FigCraft는 저장소 전체에서 이를 금지하므로 그대로 도입하기 어렵다. 의존성 수정과 앱 쪽 대응 중 어떤 방향을 택할지 관리자와 논의할 단계다.

다음 편에서는 큰 문서에서 이미지가 늦게 뜨고 확대·축소가 멈추던 문제를 다룬다.
